---
title: "obsidianlog verify"
description: "Traverse and validate the full hash chain for tamper-evidence."
---

This walks each service's SHA-256 hash chain from genesis and confirms
it's intact, proof that nothing archived has been modified, reordered,
or removed since it was written. It never decrypts log content to do
this.

## What it checks

For each service, `verify` reads the manifest's list of that service's
chunks, fetches every one, and checks that:

1. **Every chunk the manifest lists exists.** A chunk deleted from storage
   is reported as a missing chunk.
2. **Sequence numbers run without gaps or swaps.** Each chunk records its
   position in the chain, so a gap is reported as a missing chunk and
   swapped chunks as reordered chunks.
3. **Each chunk links to the one before it.** Every chunk stores the
   SHA-256 hash of its predecessor, and the first chunk links to an
   all-zero genesis hash. The hash covers the chunk's whole header
   (service, time window, sequence, previous hash, nonce, key salt,
   creation time, record count and size) and its encrypted content, so changing
   even one byte of an earlier chunk is reported as a modified chunk.
4. **The newest chunk matches the manifest.** Nothing later in the chain
   commits to the newest chunk, so its hash is checked against the head
   hash recorded in the manifest. A mismatch is reported as a head hash
   mismatch.
5. **Storage holds nothing the manifest doesn't describe.** `verify` also
   lists what's actually stored for the service and compares it with the
   manifest. A stored chunk the manifest doesn't list (for example, after
   the manifest was rolled back or restored from an older backup) fails, and
   so do two stored chunks claiming the same sequence number (a forked chain).

Across the whole archive, `verify` also:

- **Finds services the manifest has lost.** A service with chunks in
  storage but no entry in the manifest is reported as a failure, not
  skipped.
- **Checks that no two chunks were encrypted with the same key and nonce.**
  If two chunks share both, both services are reported.

So it checks both content and order, not just content.

## What it doesn't check

- **Whether the content decrypts.** `verify` doesn't need your key, so it
  can't tell whether a chunk decrypts. That check happens in
  [`query`](/cli/query): AES-256-GCM authenticates every chunk, and a chunk
  altered without the key fails to decrypt.
- **Newest chunks deleted together with a matching manifest.** A rolled-back
  manifest is caught while the newer chunks are still in storage (check 5).
  But someone who can write to both could delete a service's newest chunks
  **and** edit the manifest to match, and `verify` would still pass. They
  couldn't add or alter logs without your key, but they could drop the most
  recent ones. To catch that, keep `verify`'s output from regular runs
  somewhere else, such as CI logs. A service's chunk count should only ever
  go up.

## Flags

| Flag | Description |
| --- | --- |
| `--service <NAME>` | Restrict verification to a single service's chain. Omit to verify every service. |
| `--format <FORMAT>` | `human` (default) prints one OK/FAIL line per service. `json` prints one JSON object for CI scripts; see [JSON output](#json-output). |

Plus the global [`--config <FILE>`](/cli/overview#global-flags).

## Exit codes

`verify` exits **non-zero on any break** in any checked chain, and zero
otherwise, designed to be gated on directly in CI or a cron job:

```sh
obsidianlog verify || alert-on-call "hash chain broken"
```

## Example

```sh
# Verify everything.
obsidianlog verify

# Verify just one service.
obsidianlog verify --service api
```

For a chain that fails, `verify` prints which service and what was found (a
missing, modified or reordered chunk, a head mismatch, a chunk missing from
the manifest, a forked sequence, an unknown service, or a reused key and
nonce), rather than just a pass/fail.

## JSON output

`--format json` prints a single object. The exit code is the same as with
`human`: non-zero if any service fails.

```json
{
  "ok": false,
  "services": [
    { "service": "api", "ok": true, "chunks": 3, "head_hash": "9f2c…" },
    {
      "service": "billing",
      "ok": false,
      "error": {
        "kind": "modified",
        "position": 1,
        "sequence": 1,
        "message": "chain integrity violation: hash-chain break at position 1 (sequence 1): modified chunk"
      }
    }
  ]
}
```

- `chunks` and `head_hash` (hex, or `null` for a service with no chunks) are
  present when `ok` is `true`. Record them on each run: a service's chunk
  count should only go up, which catches the deletion described under
  [What it doesn't check](#what-it-doesnt-check).
- `error.kind` is one of the following, with these extra fields:

  | `kind` | Fields |
  | --- | --- |
  | `modified`, `reordered`, `missing`, `head_mismatch` | `position`, `sequence` |
  | `unlisted` | `window`, `sequence` (the first unlisted chunk), `count` |
  | `duplicate_sequence` | `sequence`, `count` |
  | `unknown_service` | `count` |
  | `nonce_reuse` | `sequence`, `other_service`, `other_sequence` |
  | `error` | none: verification couldn't run, for example the backend failed |

  Every error also has a human-readable `message`.
- An empty archive prints `{"ok": true, "services": []}`.

For example, to fail a CI job and list the broken services:

```sh
obsidianlog verify --format json > verify.json || jq -r '.services[] | select(.ok | not) | .service' verify.json
```
